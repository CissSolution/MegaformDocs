1.16.3

- TEMPLATE GALLERY, AND TEMPLATES THAT ACTUALLY RENDER. Until now the templates screen was an
  authoring workflow with no consumer. It has one now, and the boundary moved on purpose:
  - A gallery of complete prebuilt designs, shipped as real files in the package
    (Assets/Templates/*.html + catalog.json) rather than strings inside a .cshtml. Each card
    previews the design by RENDERING it - the same interpreter, scaled down - so a thumbnail can
    never go stale the way a screenshot does. Install copies one into the portal; Update pulls the
    packaged version again after the module improves it.
  - Two complete themes, four templates: **Newsroom** (dense news desk: lead story, ranked
    most-read rail, category strip, compact rows) and **Journal** (serif, one column, numbered
    index, drop cap, no cards). Each covers Blog Home and the article page.
  - Upload and download. Download writes the .json this screen can import back; import reads the
    file IN THE BROWSER and posts its text, so there is no upload endpoint, no temp file and no
    content-disposition to get wrong. A .json keeps name/target/notes; any other file is taken as
    a body.
  - A server-side engine that is a TWIN of the editor's preview interpreter: {{var}} {{a.b}}
    {{{raw}}} {{#each}}…{{else}}…{{/each}} {{#if}}…{{else}}…{{/if}}, values HTML-encoded, the
    triple form reserved for post.body. Both engines grew {{{raw}}} and each/else in this release
    so they stay identical.
  - The render contract is written down in catalog.json and mirrored by the editor's mock, so the
    live preview is a preview: site.*, heading, total, breaking.*, featured.*, posts[].*,
    categories[].*, pager.* / post.*, toc[], related[], tags[], comments[].
- 🔴 SAFETY, because this is the public blog: rendering happens only when the owner switches on
  "Let the active template render the blog" (Settings, default OFF) AND a template is Active for
  that target. A template that throws, or renders nothing, hands the page straight back to the
  built-in design - a mistyped {{#each}} must not blank a live blog. The active template is cached
  for 60 seconds, so a console change reaches readers within a minute instead of costing every
  anonymous request a dozen record reads. <style> inside a template is neutralised
  (expression(), javascript:, @import, </style breakouts) even though only admins can author one.
- 🔴 Two more lessons, both measured on the live site: a DNN skin styles h1..h6 DIRECTLY, and a
  direct rule beats an inherited one - a design must declare font-family on its elements, not only
  on its root, or it renders in the skin's font. And a template cannot count, so the context now
  carries pre-pluralised readsLabel / commentsLabel; "1 comments" was what the first version shipped.
- The templates screen now states what is actually live (which template renders /Blogs and the
  article page, or that the built-in design does) instead of claiming templates never render.

- Storage maintenance: "Clean unattached rows" deletes child records with no post, bounded by the
  same caps as the reads (200 images, 300 updates).

- Comments are per-post switchable, and the box on the article page is no longer unstyled.
  - The editor gained an "Allow comments on this post" checkbox. The posts form declares
    allow_comments as a Select("true"/"false") whose DEFAULT IS "false" and no console screen
    had ever written it, so a post created from the console came out with its thread shut and
    no editor had any way to open it. Create and Save now both write the field, and Create also

    rather than "comments are dead". The submit gate is now the BUTTON's own name/value, which
    a browser sends only for the button actually clicked — a hidden marker input would have
    fired on any unrelated postback of the page.
  - Every card in the list shows its comment count next to its read count, not just the
    featured one.

  correctly (244 of them on the live blog) but nothing added them up, because
  MegaForm.Core's BlogAnalyticsRollupService reads its form ids out of ManifestJson.Forms and a
  seeded blog-starter persists that array EMPTY — the service returned 0 on its second line

- Counts reads. Opening a post records a row in the blog app's `reader-events` form; MegaForm's
